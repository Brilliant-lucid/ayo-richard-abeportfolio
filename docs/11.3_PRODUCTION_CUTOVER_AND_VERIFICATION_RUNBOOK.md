# Stage 11.3 — Production Cutover & Verification Runbook

**Parent:** Stage 11 — Production Hardening & Verification  
**Status:** Execution runbook

## 1. Purpose

This is the controlled path from an approved release candidate to production. It combines final public-infrastructure verification, email/SEO checks, deployment, smoke testing, monitoring, and rollback.

## 2. Pre-cutover requirements

Do not begin cutover until:

- Stage 11.1 critical checks are complete.
- Stage 11.2 critical checks are complete.
- Stage 10 has an eligible release candidate.
- Backup/recovery path is confirmed.
- Rollback target is identified.
- Production environment variables are verified.
- Domain ownership/access is confirmed.
- Production provider access is confirmed.
- Release owner is identified.
- Support/incident contact is available.

## 3. Domain and DNS verification

Verify:

- Production domain resolves correctly.
- Required Domain Name System (DNS) records exist.
- HTTPS/TLS certificate is valid.
- Redirect behavior is correct.
- Canonical host is correct.
- Unintended development/staging domains are not presented as production.
- Authentication callback URLs use the correct production origin.
- Model Context Protocol (MCP) endpoints/callbacks use the correct origin where enabled.

## 4. Email verification

Verify the production sending domain and authentication records:

- Sender Policy Framework (SPF).
- DomainKeys Identified Mail (DKIM).
- Domain-based Message Authentication, Reporting, and Conformance (DMARC).

Test:

- Account-related email.
- Password reset.
- Notification email.
- Contact/service notification where applicable.
- Failure/retry behavior.
- Duplicate prevention.

Record provider delivery results and investigate bounce/complaint behavior.

## 5. Search and social metadata

Verify production:

- `robots.txt`.
- Sitemap.
- Canonical URLs.
- Page titles.
- Meta descriptions.
- Open Graph metadata.
- Social preview metadata.
- 404 behavior.
- Redirects.
- Indexability rules.

Test actual public portfolio URLs, project pages, Case Studies, and blogs where applicable. Do not validate only the platform homepage.

## 6. T-24 hours

- Freeze the release candidate.
- Record commit/tag.
- Capture production backup.
- Confirm rollback target.
- Confirm environment variables.
- Confirm domain/DNS/TLS.
- Confirm provider status.
- Confirm monitoring.
- Confirm support availability.
- Confirm final smoke-test checklist.

## 7. T-1 hour

- Confirm no unapproved code changes.
- Confirm release build.
- Confirm database migration status.
- Confirm backup timestamp.
- Confirm incident communication channel.
- Confirm cutover owner.

## 8. Deployment

1. Deploy the approved release candidate.
2. Confirm deployment health.
3. Apply required database migrations using the approved migration path.
4. Verify migration result.
5. Run authentication smoke test.
6. Run authorization/admin protection test.
7. Run public portfolio test.
8. Run portfolio publishing test.
9. Run project/content test.
10. Run media/storage test.
11. Run contact/service inquiry test.
12. Run email test where applicable.
13. Run MCP test where enabled.
14. Verify public SEO metadata.
15. Check application/infrastructure logs.

## 10. First hour

Monitor continuously:

- Error rate.
- Authentication failures.
- Publishing failures.
- Public-route failures.
- Database errors.
- Storage errors.
- Email failures.
- Unexpected traffic.
- Security alerts.

If a critical blocker appears, stop the rollout and execute rollback according to the approved release plan.

## 11. Rollback

Rollback decisions must distinguish application code from database state.

```text
Incident
  ↓
Assess severity
  ↓
Stop rollout
  ↓
Determine code/data compatibility
  ↓
Rollback application if safe
  ↓
Restore data only when explicitly required and safe
  ↓
Run smoke tests
  ↓
Monitor
```

Do not automatically roll back the database merely because application code was rolled back. Schema/data changes may be forward-compatible and require a controlled recovery procedure instead.

## 12. First 24 hours

Review:

- Incidents.
- Support requests.
- Critical analytics.
- Error trends.
- Infrastructure usage.
- Email delivery.
- Storage usage.
- Authentication.
- Public portfolio availability.

Record any hotfixes against the release candidate.

## 13. First 7 days

Daily review:

- Error trends.
- Authentication failures.
- Publishing failures.
- Public route failures.
- Storage failures.
- Email failures.
- Abuse reports.
- Support requests.
- Infrastructure cost/usage.

## 14. Cutover evidence

Store:

- Release commit/tag.
- Deployment timestamp.
- Migration result.
- Backup timestamp.
- Smoke-test results.
- Monitoring observations.
- Incidents.
- Rollback decision if applicable.
- Final release decision.
