# Stage 6 — Quality Assurance, Testing & Reliability Architecture

**Project:** Portfolio Platform  
**Repository:** `Brilliant-lucid/ayo-richard-abeportfolio`  
**Baseline date:** 2026-08-10  
**Program:** Production Readiness & Documentation Program (#40)

## 1. Purpose

Stage 6 establishes the quality system required to prove that the platform works reliably and that future changes do not silently break production-critical behavior.

The goal is not to create a giant test suite for every component. The goal is to protect the platform's highest-value and highest-risk behaviors first.

The Stage 5 security audit identifies automated testing as a high-priority gap because authentication, authorization, ownership, public/private filtering, uploads, inquiries, email notifications, and MCP behavior currently lack repeatable automated regression protection. fileciteturn114file0L2-L2

# 3. Quality strategy

The recommended test pyramid is:

```text
                 E2E / Browser
                ─────────────
              Critical user journeys

             Integration / API
           ─────────────────────
      Server functions + database + auth

                 Unit tests
          ─────────────────────
       Schemas, helpers, transformations
```

The platform should prioritize **security and business-critical flows over visual unit-test volume**.

# 4. Test levels

## 4.1 Static checks

Every change should pass:

- TypeScript compilation/build.
- ESLint.
- Formatting check.
- Generated artifact consistency where applicable.

## 4.2 Unit tests

Test deterministic logic without external infrastructure.

Priority examples:

- Zod schemas.
- Slug validation.
- Publication/status mapping.
- Project transformation functions.
- Legacy-to-new compatibility mapping.
- Input normalization.
- Email-header sanitization.
- Permission helper functions.

## 4.3 Integration tests

Test server functions against realistic authentication/database behavior.

Priority examples:

- Authenticated project creation.
- Ownership enforcement.
- Public portfolio resolution.
- Publication filtering.
- Contact submission.
- Service inquiry validation.
- Storage authorization.
- MCP tool authorization.

## 4.4 End-to-end tests

Test critical flows through the browser.

Priority examples:

- Sign up.
- Sign in.
- Password reset.
- Google OAuth where available in test environment.
- Complete onboarding.
- Create/edit/publish project.
- Publish portfolio.
- View public portfolio.
- Submit contact message.
- Submit service inquiry.
- Upload media.
- Delete content.
- Logout.

# 5. Test environment strategy

The test environment must not share production data or privileged credentials.

Recommended model:

```text
Local development
      ↓
Test Supabase project/environment
      ↓
Automated test database
      ↓
Ephemeral/isolated test users
```

Never run destructive authorization tests against production.

Test accounts should be synthetic and disposable.

# 6. Authentication test plan

## AUTH-001 — Sign up

Given a valid new account:

1. Submit registration.
2. Verify expected authentication state.
3. Verify portfolio onboarding behavior.
4. Verify duplicate-account handling.

## AUTH-002 — Invalid login

Given invalid credentials:

- Login must fail.
- No authenticated session must be created.
- Sensitive provider error information must not leak.

## AUTH-003 — Session expiry

Given an expired/invalid token:

- Protected server functions must reject the request.
- The application must redirect/recover appropriately.

## AUTH-004 — Password reset

Verify:

- Request accepted.
- Reset email generated by configured provider.
- Reset link reaches the expected flow.
- Password can be changed.
- Old credentials no longer authenticate where provider semantics require it.

## AUTH-005 — OAuth

Verify the complete Google OAuth callback and failure paths in a real configured test environment.

# 7. Tenant isolation test plan

This is the most important test family.

Create:

```text
User A
  Portfolio A
  Project A
  Message A
  Media A

User B
  Portfolio B
  Project B
  Message B
  Media B
```

Then attempt every cross-user operation.

### Expected result

```text
A → A = ALLOW
B → B = ALLOW
A → B = DENY
B → A = DENY
Anonymous → private = DENY
```

Test using:

- IDs.
- Slugs.
- User IDs.
- Portfolio IDs.
- Query parameters.
- Route parameters.
- MCP tool parameters.
- Storage object paths.

The test suite must deliberately attempt to bypass client-side protections.

# 8. Public visibility test plan

For every public content entity, test:

| State | Expected public behavior |
|---|---|
| Draft | Hidden |
| Published | Visible |
| Unlisted | Only according to documented link behavior |
| Archived | Hidden unless explicitly designed otherwise |
| Deleted | Not accessible |

Also test the parent portfolio's publication state.

A published project must not become public through a portfolio that is itself unpublished.

# 9. Project test plan

Project tests must cover the current migration architecture.

### Create

- Required fields accepted.
- Invalid fields rejected.
- Owner automatically assigned.

### Update

- Owner can update.
- Other users cannot update.
- Legacy compatibility behavior remains correct during migration.

### Publish

- Project becomes publicly accessible only when intended.
- Case Study representation follows `publish_as` behavior.

### Delete

- Record removed.
- Associated media/derived records handled according to lifecycle policy.

### Regression

Every future schema cleanup must run the project compatibility tests.

# 14. MCP test plan

For every registered MCP tool:

1. Valid authenticated caller succeeds.
2. Unauthenticated caller fails.
3. Expired token fails.
4. User A cannot operate on User B.
5. Invalid parameters fail validation.
6. Tool output contains only permitted fields.
7. Tool errors do not leak secrets.
8. Registry matches documentation.

The test suite should maintain a machine-readable expected tool list so documentation drift can be detected.

---

# 15. Email reliability test plan

Email should be treated as an external dependency, not as proof of database success.

Test:

```text
Database success + Email success
Database success + Email failure
Database failure + Email not attempted
```

The user-facing operation should have a documented behavior when email delivery fails.

Email content must not expose:

- service-role credentials,
- internal stack traces,
- private database IDs unnecessarily,
- secrets.

# 16. Failure-mode matrix

| Failure | Expected behavior |
|---|---|
| Database unavailable | Safe error; no secret leakage |
| Auth provider unavailable | Clear auth failure |
| Storage unavailable | Upload fails without corrupting DB state |
| Email unavailable | Primary data operation remains correctly handled; notification failure observable |
| MCP auth failure | Reject request |
| Invalid input | Validation error |
| Unauthorized record | Deny without revealing whether private record exists where appropriate |
| Unknown public slug | 404/controlled not-found behavior |
| Partial dual write | Explicit consistency/recovery behavior |

# 17. Reliability requirements

## REL-001 — No silent failure

Critical operations must either succeed or produce an observable failure state.

## REL-002 — External dependency isolation

Email, Storage, authentication, and MCP dependencies must not cause uncontrolled application crashes.

## REL-003 — Idempotency where necessary

Retries of public submissions and integrations must not unintentionally create duplicate records.

## REL-004 — Safe retry

Retry behavior must be defined separately for database writes, email delivery, uploads, and external integrations.

## REL-005 — Consistent cache invalidation

After mutations, affected queries/caches must be invalidated or refreshed so the user does not see stale content.

# 24. Bug severity model

### P0 — Release blocker

- Cross-tenant access.
- Secret exposure.
- Authentication bypass.
- Data corruption.
- Critical production outage.

### P1 — Must fix before production

- Major broken user journey.
- Incorrect public/private visibility.
- Broken publishing.
- Unsafe uploads.
- Broken account deletion.

### P2 — Should fix before/soon after launch

- Significant UX defect.
- Non-critical integration failure.
- Moderate performance issue.

### P3 — Backlog

- Cosmetic defects.
- Minor usability improvements.
- Non-critical enhancements.

# 28. Stage 6 conclusion

The platform does not need thousands of tests before launch. It needs **the right tests around the right boundaries**.

The highest-value testing investment is:

> **Authentication → tenant isolation → publication/privacy → core content management → storage → public inquiries → MCP → critical browser journeys.**

Once those are protected, the platform has a defensible quality baseline instead of relying on manual confidence.
