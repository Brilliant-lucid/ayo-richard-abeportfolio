# Stage 11.1 — Data, Security & Recovery Verification

**Parent:** Stage 11 — Production Hardening & Verification  
**Status:** Execution and evidence phase

## 1. Purpose

This document combines three closely related production concerns: production data readiness, security/abuse verification, and disaster recovery. They are grouped because all three protect the integrity, confidentiality, and recoverability of production data.

## 2. Production data cleanup

Before production cutover, inspect for:

- Test accounts.
- Demo accounts.
- Development-only records.
- Duplicate records.
- Orphaned records.
- Broken foreign-key relationships.
- Legacy fields.
- Invalid public slugs/URLs.
- Orphaned media.
- Test uploads.
- Deprecated configuration records.
- Unintended development secrets/configuration.

Do not delete production data until a backup exists and the cleanup scope is reviewed.

## 3. Migration readiness

For every schema/data migration:

1. Identify source state.
2. Identify target state.
3. Back up data.
4. Rehearse migration in a non-production environment.
5. Record before/after counts.
6. Validate relationships.
7. Validate public URLs.
8. Validate media references.
9. Validate permissions.
10. Define rollback/recovery behavior.
11. Execute production migration.
12. Run post-migration smoke tests.

The Project → Case Study/content relationships require particular attention where source-of-truth changes have occurred.

## 4. Migration evidence

Record:

- Migration identifier.
- Release commit/tag.
- Database version before.
- Database version after.
- Records before.
- Records after.
- Rows changed.
- Rows rejected.
- Media objects affected.
- Validation results.
- Rollback/recovery result.

## 5. Security verification scope

Perform production-style authorization and abuse tests against:

### Authentication

- Login.
- Logout.
- Session expiration.
- Password reset.
- OAuth edge cases.
- Account recovery.

### Authorization

- User A cannot access User B's private data.
- User A cannot edit User B's content.
- User A cannot publish User B's content.
- User A cannot delete User B's content.
- Unauthenticated users cannot access protected routes.
- Non-admin users cannot access admin functions.

### Database

- Row Level Security (RLS) policies behave as expected.
- Privileged service-role operations are restricted.
- Direct identifier manipulation cannot bypass tenant boundaries.
- Public queries return only intentionally public fields.

### Storage

- Private media cannot be retrieved by unauthorized users.
- Upload ownership is enforced.
- Delete ownership is enforced.
- File-type and size restrictions work.
- Malicious uploads are rejected or safely handled.

### Application/API

- Parameter tampering.
- Identifier manipulation.
- Mass assignment risks.
- Unauthorized state changes.
- Rate-limit bypass.
- Error information leakage.

### Model Context Protocol (MCP)

- Authentication required.
- Authorization enforced per operation.
- Read/write scope limited.
- Credentials protected.
- Administrative operations audited where applicable.

## 6. Abuse testing

Exercise:

- Sign-up spam.
- Login abuse.
- Password reset abuse.
- Contact-form spam.
- Service-inquiry spam.
- Excessive file uploads.
- Excessive AI requests.
- Excessive MCP requests.
- Malicious links/content.
- Impersonation reports.

Document the observed controls and any rate-limit gaps.

## 7. Security finding severity

**Critical:** exploitable confidentiality, integrity, authentication, or administrative boundary failure.

**High:** serious vulnerability with meaningful production impact.

**Medium:** limited impact or meaningful exploit requiring additional conditions.

**Low:** low-impact hardening issue.

Critical and normally high findings should block launch until fixed or explicitly accepted under Stage 10.

## 8. Backup requirements

Before production migration or cutover:

- Confirm database backup.
- Confirm media/storage recovery path.
- Confirm backup retention.
- Confirm access to backup credentials.
- Confirm backup timestamp.
- Confirm backup is associated with the release window.

A backup that has never been restored is an assumption, not proven recovery.

## 9. Restore drill

Perform a controlled restore:

```text
Backup
  ↓
Restore database
  ↓
Restore media
  ↓
Reconnect application
  ↓
Run migrations if required
  ↓
Run authentication test
  ↓
Run portfolio test
  ↓
Run project/content test
  ↓
Run authorization test
  ↓
Record recovery time
```

Measure:

- Recovery Point Objective (RPO): maximum acceptable data loss measured in time.
- Recovery Time Objective (RTO): maximum acceptable time to restore service.

Actual targets must be chosen based on the platform's business requirements.

## 10. Recovery validation

A restore is successful only if the recovered environment can:

- Authenticate users.
- Access correct tenant data.
- Render public portfolios.
- Render projects/content.
- Access intended media.
- Enforce authorization.
- Accept normal application operations.
